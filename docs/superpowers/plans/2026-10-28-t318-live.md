# t318 — D4 : live multi-destinations (Twitch, YouTube, Kick, RTMP) — plan d'exécution

> **Pour les agents :** sous-skill : superpowers:executing-plans (exécution directe, comme t316), puis une relecture
> finale indépendante (opus) et une vague de corrections. Cases `- [ ]` pour le suivi.

**But :** passer en direct depuis l'app : la scène de la capture (t315, habillée par le skin t316) est encodée dans la
page, envoyée par WebSocket local au backend, et UN ffmpeg la pousse en RTMP(S) vers chaque destination par le muxer
`tee` ; annonce Discord par webhook ; santé du flux, pause écran, marqueurs ; le fichier enregistré part dans la
Bibliothèque pour en tirer des clips (t317).

**Architecture :** le live est une capture t315 ordinaire (même scène, même caviardage `data-dz-secret`, même
enregistrement dans la Bibliothèque) à laquelle `dz-live.js` ajoute une SECONDE MediaRecorder sur `scene.flux()` + la
voix mixée (`__dzCapture.session().audio`), morceaux de 250 ms poussés dans un WebSocket. Côté serveur, `live.py`
résout les destinations (comptes de l'espace, secrets au coffre), lance ffmpeg (entrée pipe, libx264 + AAC, `tee`
`onfail=ignore`), lit `-progress` et les erreurs (masquées) pour la santé par destination.

**Tech :** FastAPI (WebSocket), subprocess ffmpeg 8 (rtmp/rtmps/tee), httpx (webhook), modules ES sans React.

**Spec :** `docs/superpowers/specs/2026-10-25-boite-a-outils-design.md` §8.2, §8.3, §8.6 (choix 9) ; contrats
« Contrat pour t316-t319 » (plan t315) et « Contrat pour t317-t319 » (plan t316).

## Global Constraints
- Le backend n'écoute qu'en boucle locale ; routes `/api/live` : `_require_localhost` ; WebSocket : client local ET
  en-tête Origin absent ou de même hôte.
- Destinations v1 : `twitch`, `youtube_live`, `kick`, `rtmp` (personnalisé) ; `discord` = annonce par webhook
  seulement (« Go Live » n'existe que dans le client Discord : dit en clair, jamais contourné).
- Clés de stream et webhook au coffre par `comptes.py` (`DZC_<ID>_<CHAMP>`) ; jamais dans un journal, une URL
  affichée, une réponse, un fichier `.json` (masque `••••`).
- Un seul encodage, distribué par `tee` ; latence visée < 5 s (morceaux 250 ms, `-tune zerolatency`, GOP 2 s).
- Le live encode `scene.flux()` + `session().audio` (jamais une autre composition) : le caviardage s'applique.
- « Passer en direct » est un clic explicite ; rien ne part sans lui.
- Bundle jamais reconstruit ; ce lot n'a PAS de maillon (`dzlive` non utilisé) : fichiers neufs + `index.html`.
- Textes : `frontend/shared/i18n/live.json` + `scripts/i18n_assembler.py` ; messages serveur neufs → L10.
- Preuve : port 8796, récepteurs RTMP LOCAUX lancés et arrêtés par nous, faux serveur Discord local.

## Review Focus
1. Une clé de stream qui fuit : stderr ffmpeg (« Slave '…/CLE' ») ou URL renvoyée → `masquer` sur chaque ligne ;
   test L-S3 avec une vraie erreur ffmpeg.
2. Une destination morte au départ ou en route ne coupe pas les autres (`onfail=ignore`) et apparaît « en panne » →
   test L-S5 (ffmpeg réel, une destination fermée, une locale à l'écoute).
3. Fermer l'onglet / couper la capture par la pastille : ffmpeg ne reste jamais vivant (WS fermé → `fermer`, atexit)
   → test R4 (déconnexion WS = processus fini).
4. Un compte live d'un autre espace, ou un compte non-live (x…) donné comme destination → 409/400 (test S6).
5. Une URL de serveur piégée (`|`, `[`, espaces, autre schéma que rtmp/rtmps) qui injecterait une sortie `tee` →
   refus 400 (test S2).

**Produit :** `PLATEFORMES` += `twitch` (TWITCH_STREAM_KEY secret requis, TWITCH_SERVEUR public), `youtube_live`

exclut LIVE (l'assistant d'espace, le Planificateur et les canaux de projet ne les voient jamais).

### Tâche 2 : service `live.py`
**Fichiers :** `backend/app/services/live.py`, test `test_live_service.py` ([S], [F]).
**Produit :**
- `RefusLive(ValueError)` (`statut`) ; `SERVEURS = {"twitch": "rtmp://live.twitch.tv/app", "youtube_live":
  "rtmp://a.rtmp.youtube.com/live2"}` ; `valider_serveur(url) -> str` (rtmp/rtmps, hôte, aucun de `|[]\\"' ` ni
  contrôle, ≤ 1024) ; `masquer(texte, secrets) -> str` (chaque secret et sa forme %-codée → `••••`, puis tout
  `rtmps?://…/<dernier segment>` → `…/••••`) ;
- `destinations(eid, ids) -> list[dict]` `{id, plateforme, libelle, lien, url}` (url SECRÈTE, jamais rendue par les
  routes) : compte live, du même espace (sinon 409), clé posée (sinon 400) ;
- `commande(urls, fps=30, video_kbps=4500) -> list[str]` : `ffmpeg -hide_banner -loglevel warning -nostats -progress
  pipe:1 -stats_period 1 -fflags +genpts -i pipe:0 -map 0:v:0 -map 0:a:0? -c:v libx264 -preset veryfast -tune
  zerolatency -b:v/-maxrate/-bufsize -pix_fmt yuv420p -r fps -g 2*fps -keyint_min 2*fps -sc_threshold 0 -c:a aac -b:a
  160k -ar 44100 -ac 2 -flags +global_header -f tee "[f=flv:onfail=ignore]u1|…"` ;
- `Diffusion(urls, secrets, lancer=subprocess.Popen)` : `ecrire(octets)`, `etat() -> {etat: demarrage|en_direct|
  arrete, fps, debit_kbps (entrée), images_perdues, vitesse, destinations: [ok|panne], erreur (masquée)}`, `fermer()`
  (stdin fermé, 5 s, puis kill) ; « Slave muxer #i failed » → destination i en panne ;
- registre : `ouvrir(eid, ids, titre) -> vue`, `vue(id)`, `brancher(id) -> Diffusion` (une diffusion par session,
  une session « en cours » à la fois : 409), `marquer(id, t_ms, libelle)` (200 au plus), `annoncer(id, compte, texte)`
  async (webhook `https://(discord|discordapp|ptb.discord|canary.discord).com/api/webhooks/<n>/<jeton>` ; en preuve
  `DZ_LIVE_PREUVE=1` aussi `http://127.0.0.1:<port>/api/webhooks/…` ; `allowed_mentions: {parse: []}`, pas de
  redirection, 10 s ; rend `{ok, statut}` sans URL), `terminer(id, capture_id)` (écrit
  `captures/<cid>/<cid>.dzlive.json` : `{version:1, id, titre, debut_utc, duree_ms, destinations:[{plateforme,
  libelle, etat}], marqueurs:[{t, libelle}], annonce}` sans secret), `arreter_tout()` (atexit).
- [ ] S1-S8 + F1-F3 (ffmpeg réel : une destination fermée + un récepteur local `-listen 1` ; masquage du stderr ;
